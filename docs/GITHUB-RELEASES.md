# Публикация OVF UI и проверка обновлений

Проверка обновлений читает публичный стабильный GitHub Release из [RareMxxx/OVF-UI](https://github.com/RareMxxx/OVF-UI). Репозиторий закреплён в коде. Поля ввода адреса нет; старое значение github_repository в настройках и импортируемых подключениях игнорируется.

Приложение не загружает и не запускает обновление автоматически. Кнопка открывает проверенную HTTPS-страницу выпуска на `github.com` в закреплённом репозитории. Токены и пароли Cloud Director для GitHub не используются.

Проверка работает **без авторизации в GitHub**: отдельный HTTPS-клиент делает только GET к `api.github.com/repos/{owner}/{repository}/releases/latest`. Он не читает GitHub CLI, Git credential helper, браузерные cookies, ключи публикации или системное хранилище секретов. В запросе нет заголовка Authorization, содержимого настроек, имён тенантов и адресов ЦОДов. GitHub получает адрес закреплённого публичного репозитория, версию OVF UI в User-Agent и обычные сетевые сведения (например, внешний IP).

TLS-сертификат проверяется, HTTP и перенаправления запрещены. Ответ ограничен 1 МиБ и таймаутом 25 секунд. Ссылка выпуска сверяется с закреплённым репозиторием; черновики и предварительные версии отклоняются. При лимите анонимного API приложение сообщает об ошибке и не предлагает вводить токен. Подключённый к Codex GitHub нужен для публикации разработчиком и не является частью дистрибутива.

Скрипт сборки создаёт ZIP из новой временной папки по явному списку файлов: содержимое папки запущенного приложения в архив не подмешивается. Рядом создаётся `SHA256SUMS.txt`. Контрольная сумма помогает проверить целостность, но не заменяет цифровую подпись издателя; автоматическая установка и проверка подписи в этой версии не реализованы.

Текущий выпуск — только **Windows x64**, с основным сценарием работы в **MWS Cloud Director, облаке на базе VMware**. Linux пока не выпускается.

Для поля **About → Description** репозитория:

> Интерфейс для VMware OVF Tool на Windows: загрузка и скачивание OVA, OVF и ISO. В первую очередь адаптирован под MWS Cloud Director.

Workflow использует `contents: read`, не публикует код или релизы и не получает облачные секреты. Checkout не сохраняет GitHub-токен в Git-конфигурации; Actions закреплены по SHA коммита. Это ограничивает права сборки, но не заменяет защиту самого аккаунта GitHub. Используйте двухфакторную аутентификацию или passkey, а подключению для публикации предоставляйте доступ только к нужному репозиторию. Настройки аккаунта приложение не меняет.

## 1. Создайте репозиторий

1. Войдите в GitHub и выберите **New repository**.
2. Укажите имя, например `ovf-ui`, и доступ **Public**. Приватный репозиторий без отдельной авторизации GitHub не поддерживается проверкой обновлений.
3. Если отправляете существующий проект, не добавляйте при создании пустого репозитория README и лицензию: они уже находятся в проекте.
4. Через GitHub Desktop добавьте локальную папку проекта и свяжите её с созданным репозиторием. Либо используйте подсказки GitHub для отправки существующего репозитория через Git.
5. Перед коммитом просмотрите список файлов. Публикуются исходники, `Cargo.toml`, `Cargo.lock`, `README.md`, `LICENSE`, `docs`, тестовые фикстуры без секретов и `.github`. Локальные настройки, журналы, архивы подключений, дампы API, изображения клиентов, ISO/OVA/OVF/VMDK, `.local`, `target`, `dist` и OVF Tool публиковать не надо. Проверьте также содержимое уже отслеживаемых файлов: `.gitignore` не удаляет их из истории.

OVF Tool устанавливается пользователем отдельно; дистрибутив Broadcom не входит в релиз OVF UI.

### Публикация без плагина

Для отправки исходников через Git по HTTPS и загрузки ZIP в Release через GitHub API можно использовать отдельный fine-grained personal access token. Выберите только репозиторий `OVF-UI`, короткий срок действия и права `Contents: write`. Для добавления или обновления `.github/workflows` потребуется также `Workflows: write`. Доступ ко всем репозиториям, права администратора и секреты Cloud Director не нужны.

Токен храните в диспетчере учётных данных Windows как отдельные общие учётные данные, например `OVF-UI-GitHub-Publish`. Не вставляйте его в чат, исходники, remote URL, параметры команд или файлы проекта. Эта запись предназначена только для локальной публикации разработчиком; приложение её не читает. После публикации одноразовый токен можно отозвать на GitHub.

Вспомогательные `examples/qa_*.rs` привязаны к локальному приёмочному стенду и исключены из Git через `.gitignore`. Они не нужны для сборки приложения. Не публикуйте их вместе с локальными протоколами тестирования и адресами клиентской инфраструктуры.

## 2. Подготовьте версию

1. Измените `version` в секции `[package]` файла `Cargo.toml`. Используйте три числа: например `0.5.0`. Обновите README и примечания к версии.
2. После изменения зависимостей обновите `Cargo.lock` обычной локальной сборкой. Для фиксированной проверки затем используйте:

   ```text
   cargo fmt --all -- --check
   cargo test --locked --features test-fixtures
   cargo clippy --locked --all-targets --features test-fixtures -- -D warnings
   pwsh -File ./scripts/build-release.ps1
   ```

3. Отправьте коммит. Вкладка **Actions → Build and test** собирает Windows x64. Дождитесь зелёного результата.
4. Скачайте артефакт `OVF-UI-Windows-x64` из завершённого запуска. Это архив сборки, ещё не опубликованный релиз.

Существующий workflow `.github/workflows/build.yml` не создаёт релизы автоматически. Это позволяет проверить готовые файлы перед публикацией.

Публичный EXE собирается через `scripts/build-release.ps1`: `--remap-path-prefix` заменяет пути профиля, Cargo, Rustup, исходников и build-каталога на нейтральные. `scripts/check-build-paths.ps1` отклоняет результат, если локальные пути остались. Скрипт упаковки проверяет также остальные файлы архива. Настройки и папка загрузки пользователя вычисляются приложением при запуске и не зависят от этих диагностических путей.

## 3. Проверьте архив Windows

- **Windows:** архив должен содержать `ovf-ui.exe`, README и лицензию. При локальной LLVM-сборке из `scripts/build.ps1` переносите весь созданный дистрибутив, включая `libunwind.dll` и лицензии; не заменяйте его единственным exe. Сборка GitHub на MSVC отличается от локальной LLVM-сборки.
- Проверьте запуск Windows-сборки, выбор папки OVF Tool, настройки, обе темы и реальные базовые сценарии на тестовом окружении.
- Включите сведения о сторонних лицензиях, если используемый способ упаковки их формирует. До публикации проверьте комплектность runtime-зависимостей и лицензий; CI-артефакт является исходной сборкой, а не установщиком.
- Добавьте SHA-256 архива в описание релиза или приложите `SHA256SUMS.txt`: `Get-FileHash -Algorithm SHA256 <архив>`. Контрольная сумма обнаруживает повреждение скачивания; цифровую подпись издателя она не заменяет.

## 4. Опубликуйте Release

1. Откройте **Releases → Draft a new release** в репозитории.
2. Создайте тег, совпадающий с версией пакета: для `version = "0.5.0"` — `v0.5.0`. Выберите проверенный коммит.
3. Назовите выпуск `OVF UI 0.5.0`, опишите изменения, требования, известные ограничения и результаты Windows-проверок.
4. Прикрепите архив `OVF-UI-0.5.0-windows-x64.zip` и контрольные суммы.
5. Для стабильного канала не включайте **Set as a pre-release**. Пометьте выпуск **Latest**, если интерфейс GitHub предлагает этот выбор, и нажмите **Publish release**.

Черновик и pre-release не будут предложены как стабильное обновление. Предварительные сборки можно публиковать отдельно с тегом `v0.6.0-rc.1` и флагом pre-release, но текущий проверяющий модуль не использует этот канал.

## 5. Проверьте уведомление в приложении

1. В настройках нажмите «Проверить обновления». Вход в GitHub не требуется.
2. На старой версии приложения должен появиться новый выпуск и ссылка на его страницу. На той же версии обновление не предлагается; сравнение SemVer учитывает числа (`0.10.0` новее `0.9.0`), а не порядок строк.
3. При переносе репозитория разработчик должен изменить закреплённый адрес и выпустить новую сборку. Автоматические HTTP-перенаправления при проверке отключены.
4. Ошибка 404 означает, что репозиторий недоступен публично, адрес неверен или стабильный Release ещё не опубликован. При 403/429 GitHub мог ограничить число запросов: повторите позже. Ошибка сети не означает, что версия актуальна.

Официальные инструкции: [управление релизами GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository), [API последнего стабильного выпуска](https://docs.github.com/en/rest/releases/releases#get-the-latest-release). `latest` здесь означает выпуск, выбранный GitHub для стабильного канала, а не поиск наибольшего тега среди всех веток.
