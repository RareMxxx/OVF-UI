OVF UI 0.4.0 — проверка функциональности и производительности
Дата: 01.11.2026

Границы проверки
Проверены исходники всех модулей, автоматические тесты, локальный HTTPS-стенд,
локальная модель multipart-хранилища, установленный OVF Tool 9.1.1 (--help),
интерфейс на демонстрационных данных. Запросов в пользовательский Cloud Director
в рамках этой проверки не выполнялось. Ни ВМ, ни ISO, ни каталоги ЦОДа не менялись.
Это перечень проверенных сценариев и известных границ, а не гарантия всех
возможных сочетаний конфигураций провайдеров.

1. Исправленные несостыковки

• Кнопки и поля использовали разные радиусы и размеры. Теперь основные элементы
  имеют общие параметры: высота 36 px, радиус 18 px; карточки — 12 px.
  Для компактных значков сохраняется соответствующий им размер.
• В светлой теме второстепенный текст был слишком бледным. Цвета текста,
  состояния успеха и предупреждения теперь зависят от темы; границы усилены.
• Каталоги занимали по строке каждый. Теперь это сетка с пересчётом количества
  столбцов по ширине окна, Owner под названием, длинные строки сокращаются
  с полным текстом в подсказке. При большом числе каталогов прокрутка тонкая.
• Большая анимация проверки версии и ручная кнопка убраны из боковой панели.
  Там только версия, latest / +upgrade, маленькое многоточие во время проверки
  и OK/OFF. Ручная проверка находится в настройках.
• У ВМ показываются vCPU, RAM и ёмкость дисков. Неизвестное значение — «—»,
  а не нулевой ресурс. API VmSpecSection уточняет данные Query API.
• Ошибка экспорта отдельной ВМ из многомашинного vApp открывает модальный диалог.
  Полный текст можно скопировать; строка состояния не растягивается длинной ошибкой.
• Перед запуском из очереди повторно проверяются состав vApp, питание и ISO.
  Новая соседняя ВМ, сменившийся носитель или включение ВМ требуют нового просмотра.
• Проверку пакета можно было обойти кнопкой загрузки. Локальная структурная
  проверка и контрольные суммы теперь обязательны перед импортом.
• OVA с ISO, ссылка *.iso в OVF (включая кодированный путь и разный регистр)
  и подключённый CD/DVD через HostResource отклоняются до импорта.
  Пустой CD/DVD-привод и отдельный ISO как media поддерживаются.
• После скачивания пакет также проверяется до финального переименования и S3.
  Некорректный пакет остаётся в .partial, успех не показывается.
• Результат проверки ранее выбранного файла больше не помечает новый файл
  проверенным, если пользователь сменил путь во время проверки.

2. Новый сценарий «Через шаблон в каталоге»

Выбор vApp → просмотр состава и ISO → выбор каталога и имени → явный запуск →
повторная проверка → согласованное извлечение ISO → captureVApp → ожидание Task →
проверка готовности шаблона и его появления в Query API → скачивание OVF Tool →
локальная проверка → завершение или отправка в S3.

• API-ссылки операций берутся из ответов vCD, проверяется origin.
• Шаблон сохраняется в каталоге. Это написано в диалоге и журнале.
• Нет автоматического удаления шаблона или перезаписи TargetCatalogItem.
• Имена новых шаблонов по умолчанию содержат случайный суффикс.
• Совпавшее имя шаблона, неоднозначный каталог, отсутствие прав или несовпадение
  адреса результата задачи останавливают процесс с объяснением.
• При отмене ожидания задача в vCD может продолжаться; это сообщается пользователю.
• Повтор после ошибки не должен создавать дубликат: существующее имя блокируется.
  После завершившегося захвата следует обновить каталог и скачать готовый шаблон.

3. ISO и питание

• Читаются MediaImage из VmSpecSection и ссылки CD/DVD из старой hardware-секции.
• Несколько ISO отображаются отдельными строками. Извлечение разрешено только
  после подтверждения списка в форме. Перед POST носитель и питание перечитываются.
• Неизвестный backing, отсутствие конфигурации носителей или адреса ISO блокируют
  автоматический экспорт; потребуется извлечение в vCD и повторная проверка.
• Успешная задача извлечения дополнительно проверяется чтением конфигурации ВМ.
• ISO не удаляется из каталога и не подключается обратно автоматически.
• Если дальнейший захват/скачивание не удался, уже извлечённый ISO остаётся извлечённым.
• Power Off по-прежнему требует отдельного подтверждения. Это принудительное
  выключение, не штатное завершение гостевой ОС. Автоматического включения нет.
• Экспорт отдельной ВМ из vApp с соседями не реализован: API захвата и OVF Tool
  работают с vApp целиком. Нужно явно выбрать весь vApp либо выделить ВМ отдельно.
  CaptureVmParams не используется как недокументированный фильтр состава vApp.

4. Производительность

• Передача Cloud Director ↔ OVF Tool остаётся потоковой: бинарные данные идут
  через Bytes без накопления полного файла и без дополнительной записи прокси на диск.
• При лимите 0 ограничитель немедленно возвращает управление: нет искусственного
  ожидания на каждом блоке. Метаданные буферизуются отдельно, с пределом 16 МиБ.
• Для loopback-соединений включён TCP_NODELAY; upstream использует повторные
  соединения и пул до 16 неактивных соединений на узел.
• Добавлен --parallelThreads: 4 по умолчанию, выбор 1–16 в форме, 1 для совместимости.
  Для старой/нераспознанной версии OVF Tool приложение выбирает 1.
  Это запрос параллельности к OVF Tool, не обещание четырёх потоков для одного OVA
  или одного диска. Эффект для конкретного vcloud endpoint нужно измерять отдельно.
• Дополнительное --compress=9 не включается: сильное сжатие может ограничить CPU.
  Внутренние преобразования дисков OVF Tool / ESXi остаются частью экспорта.
• S3 раньше передавал части последовательно. Теперь до 4 частей по 16 МиБ
  выполняются одновременно. Для обычных образов полезные буферы ограничены 64 МиБ;
  транспортные буферы добавляются отдельно. Для очень больших объектов размер
  части растёт, число потоков снижается до одного, чтобы не превысить 10 000 частей.
  При объекте 5 ТиБ одна часть может занимать около 525 МиБ памяти.
• Ограничитель S3 общий для частей. Счётчик растёт после подтверждения части;
  поэтому скорость может выглядеть ступенчатой. Внутри части возможны всплески.
• Полная проверка SHA1/SHA256 читает образ с диска. Это отдельный этап после
  скачивания / перед импортом; он увеличивает общее время, но не задерживает
  сетевые блоки в момент передачи.
• Локальный синтетический тест 32 МиБ: отладочная сборка, без диска и ЦОДа:
  напрямую TLS около 250 МиБ/с, через TLS-прокси OVF UI около 180 МиБ/с.
  Это разовый диагностический замер, не эталон и не гарантия для 10/25 GbE.
  Дополнительное TLS-шифрование и обработка прокси имеют измеримые накладные расходы.
• Отдельный прогон оптимизированной release-сборки, 32 МиБ, без диска и ЦОДа:
  скачивание напрямую TLS — 704,9 МиБ/с, через прокси — 478,0 МиБ/с;
  загрузка напрямую TLS — 655,5 МиБ/с, через прокси — 452,1 МиБ/с.
  Эти числа относятся к синтетическому потоку на данном компьютере. Они не
  включают преобразование OVA/VMDK, производительность накопителя и внешней сети.

Практический режим: лимит 0, актуальный OVF Tool, достаточно быстрый локальный диск,
несколько потоков для поддерживаемой передачи. Одновременные задания делят сеть,
CPU и накопитель; увеличение их числа не гарантирует ускорения одного задания.
Максимальную скорость пользовательского ЦОДа без реальной передачи установить нельзя.

5. Проверенные существующие механизмы

Итог: 35 автоматических тестов (34 модульных/HTTPS/S3 и 1 с реальным подпроцессом),
Clippy без предупреждений, rustfmt. Дополнительно пройден целевой release-тест
потоковой передачи в обоих направлениях. UI проверен в двух темах, узком и широком
окне, включая ресурсы ВМ, сетку каталогов, диалог нескольких ВМ и форму шаблона/ISO.

• Согласование версии API и versioned Accept для OVF Tool 9.1.1.
• Локальный session ticket, TLS-прокси и непередача облачных токенов внешнему
  transfer-host. Запрет команд выключения целого vApp со стороны OVF Tool.
• Пагинация инвентаря, отбор каталогов с Owner, ёмкость дисков ВМ.
• Проверка пути, свободного места и резерва; учёт параллельных задач данного процесса.
• Задачи Preparing/Transferring/Processing удерживают очередь до завершения vCD.
• После импорта ожидаются задачи, готовый ресурс и два последовательных подтверждения.
• Машинный вывод OVF Tool, ошибки API, редактирование секретов в журнале.
• Манифест, размеры файлов, traversal-пути и отказ от ссылок/спецфайлов внутри OVA.
• Шифрование экспортируемых подключений и обнаружение неверного пароля.
• S3 multipart: порядок частей, счётчик завершённых байтов, отмена, уникальные ключи.

6. Ограничения и дальнейшие проверки

1) Приёмочный импорт/экспорт на реальном vCD и реальном S3 в этой версии не запускался.
   Тестовый сервер не заменяет проверку прав, квот, storage policy и особенностей ЦОДа.
2) Захват через шаблон требует дополнительного места в каталоге. Квота ЦОДа заранее
   полностью не рассчитывается; отказ сервера отображается в задаче.
3) Между финальной проверкой ВМ и действием другого администратора остаётся гонка:
   vCD не предоставляет приложению транзакционную блокировку всего сценария.
4) При сетевом обрыве после POST сервер мог принять операцию. POST автоматически
   не повторяется. Перед ручным повтором нужно проверить задачи и каталог.
5) Обычная загрузка в существующий каталог также не делает атомарной предварительную
   проверку совпадения имён. Флаг overwrite отсутствует, окончательное решение — у vCD.
6) Остановленная передача не возобновляется с байта обрыва. Повтор начинает заново.
   После перезапуска сохраняется история, но не автоматический повтор с секретами.
7) API Bearer token невозможно обновить без refresh token. Долгая операция может
   потребовать нового входа; это не устраняется увеличением числа потоков.
8) Число байтов диска — I/O процесса OVF Tool с учётом кэша ОС, не физический benchmark.
   Выделенный объём дисков и итоговый размер сжатого OVA могут значительно отличаться.
9) Резервы диска учитываются внутри одного экземпляра приложения. Два одновременно
   запущенных экземпляра не делят общий реестр резервов и могут спорить за settings/history.
10) При ошибке S3 локальная копия сохраняется, однако отдельной кнопки «повторить только
    S3» пока нет: общий повтор может заново скачать образ. При аварийном выходе могут
    остаться незавершённые multipart-части; нужна lifecycle-политика бакета.
11) Изменение лимита во время сна уже запланированного блока может примениться
    с задержкой до конца этого блока. Новый запуск с лимитом 0 не ограничивается.
12) Вложенные нестандартные структуры OVA/манифеста, подписанные пакеты, vTPM,
    шифрование, независимые диски и специфические сети требуют отдельного импорта
    на стенде. «Проверка пройдена» не гарантирует аппаратную совместимость ЦОДа.
13) Owner является критерием показа, а не доказательством права записи. Опубликованный
    или общий каталог с Owner может быть доступен только на чтение; ошибка API сохраняется.
14) Linux, другой масштаб DPI, прокси организаций и все разновидности S3-провайдеров
    в текущей Windows-среде не проверены.
