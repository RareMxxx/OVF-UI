# OVF UI

**OVF UI — приложение для Windows, с которым можно загружать и скачивать образы в Cloud Director без ручного ввода команд OVF Tool.**

В первую очередь проект адаптирован под **MWS Cloud Director — облако на базе VMware**. Интерфейс и рабочие процессы ориентированы на повседневные задачи в MWS: подключиться к нужному ЦОДу, выбрать тенант и каталог, перенести образ и увидеть, на каком этапе находится передача. Совместимость с другими провайдерами Cloud Director требует отдельной проверки.

OVF UI берёт на себя выбор параметров и запуск **VMware OVF Tool**. Вы выбираете объект и место назначения, а приложение проверяет пакет, доступное место и совпадения имён, показывает скорость и сохраняет журнал. Сами образы между компьютером и Cloud Director передаёт OVF Tool; API используется для работы с инвентарём и задачами облака.

Текущая версия — **0.5.0 preview**, платформа выпуска — **Windows x64**. Интерфейс на русском, доступны светлая и тёмная темы с красным акцентом. OVF Tool устанавливается отдельно. Linux пока не входит в поддерживаемый выпуск.

## Что можно делать

- Хранить подключения к нескольким ЦОДам и переключаться между тенантами.
- Просматривать vApp, ВМ, каталоги, шаблоны и ISO.
- Загружать OVA, OVF и ISO в каталог, скачивать vApp и шаблоны на компьютер.
- Экспортировать vApp через предварительное создание шаблона в каталоге.
- Проверять пакеты, свободное место и занятые имена перед передачей.
- Запускать передачи по очереди или одновременно, менять ограничение скорости.
- Отправлять скачанный образ в S3 через локальную промежуточную копию.

Приложение написано на Rust с нативным интерфейсом egui. Установщик и права администратора для обычного запуска не нужны.

Сборки размещаются в [Releases](https://github.com/RareMxxx/OVF-UI/releases). Если опубликованного выпуска ещё нет, приложение можно собрать из исходников по инструкции ниже. Предварительная версия предназначена для проверки на тестовом окружении перед использованием в рабочих задачах.

## Быстрый старт

1. Распакуйте весь архив Windows-сборки и запустите `ovf-ui.exe`. Не переносите один `.exe` отдельно от остальных файлов.
2. При первом запуске выберите папку с `ovftool.exe`. Папка и версия проверяются и запоминаются.
3. Добавьте endpoint: название и полный HTTPS-адрес Cloud Director. Адрес портала с `/tenant/...` также принимается: приложение использует origin сервера.
4. Укажите точное имя организации и логин/пароль, API refresh token или временный Bearer token. Подключения отображаются слева: endpoint → тенанты. Секрет вводится один раз.
5. Выберите «Виртуальные машины» либо «Каталоги и образы». Кнопка «Скачать» открывает проверку состава vApp, пути, размера и свободного места.
6. Для импорта выберите «Загрузить в каталог», локальный файл, каталог, виртуальный ЦОД и имя. При необходимости создайте каталог через кнопку в диалоге.

Если уже есть активная передача, приложение предлагает очередь или одновременный запуск. Все передачи отображаются в отдельном системном окне.

Шкала передачи состоит из подготовки (0–5%), передачи файлов (5–95%) и финальной обработки (95–99%). Точный процент текущего этапа Cloud Director показывается отдельно, если API его сообщает. Для неизвестного прогресса подготовки показывается 0,1% и название этапа. 100% и «Завершено» появляются после успешного OVF Tool и подтверждения Cloud Director; при импорте также проверяется готовность созданного шаблона или ISO. Ожидание до двух часов, отмена не отменяет автоматически задачу в ЦОДе.

Рядом с версией OVF Tool показаны `latest` или `+upgrade`. Проверка на официальной странице Broadcom выполняется при запуске, в полночь по времени компьютера и вручную в настройках. Фоновый таймер работает и при свёрнутом окне; после сна проверка выполняется при пробуждении. `+upgrade` открывает страницу загрузки в браузере. Обновление устанавливается пользователем. При недоступности Broadcom выводится компактный знак `?` с причиной ошибки, без неподтверждённой отметки `latest`.

Для переноса на другой Windows-компьютер используйте весь архив `dist/OVF-UI-0.5.0-windows-x64.zip`. В LLVM-сборке рядом с `.exe` необходим `libunwind.dll`; отдельно переносить только `.exe` не следует. Установщик и права администратора для запуска не нужны.

## Реализованные сценарии

- Сохранение нескольких endpoint и нескольких тенантов на каждом endpoint.
- Вход по паролю, обмен API refresh token на access token, вход по готовому Bearer token.
- Согласование поддерживаемой API-версии в диапазоне 33.0–39.0; чтение инвентаря с пагинацией.
- Списки vApp, ВМ, каталогов, шаблонов и ISO; поиск и фильтрация по каталогу.
- Экспорт vApp и шаблонов в OVA/OVF, экспорт media в ISO через OVF Tool.
- Импорт OVA/OVF в шаблон каталога и ISO в media через OVF Tool. Автоматическая перезапись существующего объекта отключена.
- Создание неопубликованного каталога через API с правами пользователя.
- Скачивание в локальную папку или в S3 через локальную промежуточную копию.
- Проверка доступности папки для записи и свободного места, резерв по умолчанию 2 ГиБ, учёт других передач на том же томе. Дополнительная проверка свободного места во время скачивания.
- Очередь, параллельные операции, отмена, повтор с начала, журнал и история передач. После перезапуска прерванная задача не запускается автоматически.
- Процент из machine output OVF Tool, скорость потока данных, скорость записи процесса и время работы. Лимит скорости можно менять во время передачи.
- Отдельная кнопка проверки: чтение пакета, структура XML, наличие файлов, размеры, SHA1/SHA256 манифеста, затем `ovftool --verifyOnly` для OVA/OVF. OVA проверяется без извлечения дисков на файловую систему.
- Локальное хранение секретов и зашифрованный экспорт/импорт подключений, включая S3.

## Токен и OVF Tool

API refresh token сначала обменивается на Bearer token через `/oauth/tenant/{org}/token`. Приложение обновляет его до истечения `expires_in`, в том числе фоновым таймером во время длительного потока. Одновременные запросы используют одно обновление. Безопасный повтор после HTTP 401 разрешён только для чтения: поток загрузки PUT/POST автоматически не воспроизводится. Готовый временный Bearer token без refresh token автоматически продлить нельзя.

OVF Tool запускается с интеграционным session ticket локального адаптера. Для каждой передачи создаётся отдельный HTTPS-адаптер на **127.0.0.1 и случайном порту**, ключ на время передачи и временный сертификат. OVF Tool получает отпечаток именно этого сертификата. Адаптер подставляет действующую авторизацию при обращении к Cloud Director и переписывает ссылки на файлы.

Проверка TLS upstream-сервера остаётся включённой; системное хранилище сертификатов не изменяется. Облачный пароль, refresh token и access token не передаются в аргументах OVF Tool. Для внешних transfer-hosts не пересылается Authorization Cloud Director. Данные читаются и записываются потоково, с ограничением скорости и подсчётом байтов.

Это адаптер совместимости, а не штатная поддержка refresh token самим OVF Tool. Протокол проверен на локальном HTTPS-стенде и полным экспортом vApp в OVA через OVF Tool 9.1.1 на пользовательском Cloud Director (API 39.0). Запросы OVF Tool без версии API дополняются согласованной версией, чтобы избежать HTTP 406. Другие провайдеры и версии требуют отдельного приёмочного прогона.

## Работа с vApp

В диалоге скачивания доступны прямой экспорт и «Через шаблон в каталоге». Во втором случае создаётся новый шаблон, ожидается завершение задачи и готовность ресурса, затем запускается OVF Tool. Шаблон сохраняется в каталоге; его создание требует места и прав в ЦОДе. Существующие шаблоны не перезаписываются.

Подключённые ISO показываются до начала передачи. Для извлечения требуется явная отметка в форме. После извлечения ISO остаётся в каталоге и не подключается обратно автоматически. Неизвестный носитель или изменившийся состав vApp требуют повторной проверки. OVA/OVF со ссылками на ISO не проходят проверку; пустой CD/DVD-привод допускается. Локальная проверка выполняется также автоматически перед импортом и после скачивания.


Экспорт Cloud Director через OVF Tool выполняется на уровне vApp. Если в выбранном vApp одна ВМ, можно начать экспорт из строки этой ВМ. Если в vApp несколько ВМ, экспорт отдельной ВМ блокируется с объяснением: выберите vApp целиком либо заранее выделите ВМ в отдельный vApp.

Приложение показывает состав vApp. Для **Power Off** требуется отдельное подтверждение списка включённых ВМ; это принудительное выключение без завершения гостевой ОС. Перед выполнением список перечитывается. API вызывается для конкретных подтверждённых ВМ, а не для всего vApp. Перед фактической передачей состояние проверяется ещё раз. Адаптер запрещает команды выключения/undeploy от OVF Tool.

Приложение не включает ВМ автоматически после экспорта. Восстановление питания остаётся явным действием пользователя в Cloud Director.

## Производительность

Лимит 0 означает отсутствие ограничения приложения. Поле «Потоки OVF Tool» задаёт 1–16 потоков, по умолчанию 4; доступная параллельность зависит от формата, OVF Tool и сервера. Прокси передаёт бинарные данные потоково и использует TCP_NODELAY. S3 отправляет до четырёх частей одновременно с ограничением памяти. Проверка контрольных сумм — отдельный этап чтения с диска. Скорость конкретного ЦОДа без реального прогона не гарантируется.

Подробный разбор сценариев, результатов и оставшихся ограничений: [FUNCTIONAL-REVIEW-0.5.0.txt](FUNCTIONAL-REVIEW-0.5.0.txt).

## Место в каталоге и совпадение имён

Перед импортом или захватом в шаблон проверяются все элементы целевого каталога, его дисковая политика и доступная квота. Для OVF/OVA используется сумма заявленных ёмкостей дисков, а не только размер сжатого файла. Если каталог наследует политику, она определяется через выбранный vDC и его единственную политику по умолчанию. Неизвестная квота обозначается явно и требует отдельного подтверждения; известная нехватка блокирует запуск.

Проверка выполняется повторно при старте из очереди. Имя и облачное место резервируются между заданиями приложения. Сравнение имён учитывает регистр и Unicode-нормализацию. Перезапись существующего образа отключена. Другие клиенты Cloud Director могут изменить каталог или квоту после проверки: API не предоставляет общей атомарной блокировки для этих операций. Окончательный отказ сервера показывается как ошибка, а не успешная передача. Квота тенанта не равнозначна физически свободному месту провайдера.

## Обновления приложения

Вход в GitHub и токен не нужны. Проверка читает только публичные релизы через отдельный HTTPS-клиент; данные подключений, пароли и токены Cloud Director/S3 в GitHub не отправляются. Доступ разработчика для публикации в приложение не включён. При ограничении запросов приложение предлагает повторить проверку позже, без запроса авторизации.

Источник обновлений закреплён в приложении: [RareMxxx/OVF-UI](https://github.com/RareMxxx/OVF-UI). Изменить его через настройки, импорт подключений или старый settings.json нельзя. Стабильный Release проверяется при запуске, ежедневно около 00:00 по локальному времени и после пробуждения. Кнопка «Проверить обновления» запускает проверку вручную. Новая версия открывает страницу выпуска; автоматической установки нет. Инструкция по публикации: [docs/GITHUB-RELEASES.md](docs/GITHUB-RELEASES.md).

## S3

В настройках задаются HTTPS endpoint, регион, существующий бакет, префикс, access key, secret key и необязательный session token. Используется path-style адресация. Новый бакет автоматически не создаётся.

Путь: Cloud Director → **OVF Tool → локальный OVA/ISO** → multipart upload S3. Для S3 выбирается OVA либо ISO; набор OVF+VMDK сохраняется локально. Имена S3-объектов включают уникальный идентификатор передачи, чтобы не перезаписывать предыдущие экспорты. После завершения проверяется размер объекта. При отмене или ошибке выполняется попытка abort multipart; при аварийном завершении процесса могут остаться части.

Локальная копия сохраняется как при успешной отправке, так и при ошибке S3. Нужное место проверяется до запуска OVF Tool. Ограничение скорости S3 применяется в среднем по частям; внутри одной части возможен краткий всплеск. Сетевой счётчик S3 обновляется после подтверждения части сервером.

S3 имеет отдельный транспорт, поскольку OVF Tool не является клиентом S3. Передача между Cloud Director и локальным образом выполняется только OVF Tool.

## Хранение данных

- Настройки: `settings.json` в локальном каталоге данных приложения.
- После переименования в OVF UI сохранены прежний каталог данных `OVFDock/OVF Dock`, служба системного хранилища секретов и формат `.ovfdock`. Переносить настройки вручную не нужно.
- Секреты: Windows Credential Manager. Небезопасного fallback в открытый JSON нет.
- Экспорт `.ovfdock`: Argon2id (64 МиБ, 3 прохода) + AES-256-GCM; случайные salt и nonce, пароль от 12 символов. Импорт добавляет подключения с новыми идентификаторами.
- История: `transfers.json`; журнал: `ovf-dock.log` и предыдущий файл. URL с параметрами, пароли и токены маскируются. До 200 записей истории; до 120 строк на передачу; ротация журнала после 4 МиБ.
- Неполная загрузка: `.ovfdock-<id>.partial` в выбранной папке. После успеха папка переименовывается. Неполные данные автоматически не удаляются.
- `OVF_DOCK_DATA_DIR` задаёт отдельный каталог данных для тестирования. Секреты всё равно хранятся в системном хранилище.
- Версия 0.5 допускает один экземпляр приложения на пользователя ОС, включая разные каталоги тестовых настроек. Второй запуск показывает диалог; блокировка снимается ОС после завершения или сбоя. Старые версии без этой блокировки нужно закрыть перед запуском новой.

Хранилище Windows защищает сохранённые секреты средствами ОС. Программа не может защитить их от вредоносного ПО с правами вашего пользователя или администратора. Перед публикацией журналов и экспортом подключений проверяйте, какие данные вы передаёте.

## Сборка

Нужен актуальный stable Rust с поддержкой edition 2024 и let-chains. Зависимости фиксируются `Cargo.lock`.

Windows (обычный вариант: Rust MSVC + Visual Studio C++ Build Tools):

```powershell
pwsh -File ./scripts/build-release.ps1
cargo test --locked --features test-fixtures
```

В текущем workspace также настроен автономный LLVM-MinGW в `.tools`, с отдельным Rust toolchain `stable-x86_64-pc-windows-gnullvm`. Он используется скриптами без изменения системного PATH:

```powershell
./scripts/build.ps1
./scripts/check.ps1
```

Для публичной сборки используйте PowerShell 7 и эти скрипты: они заменяют локальные пути компилятора нейтральными `/build/...` и проверяют результат перед упаковкой. Обычный `cargo build` предназначен для разработки и может оставить пути исходников в диагностических строках EXE. Это не влияет на выбор папок пользователем: настройки и загрузки определяются во время работы для его учётной записи Windows.

GitHub Actions в `.github/workflows/build.yml` описывает сборку и проверки Windows x64. Наличие workflow само по себе не означает, что удалённая CI-сборка уже выполнялась. Платформенный код Linux сохранён для будущей работы; сборки Linux сейчас не выпускаются.

## Границы первой версии

- В версии 0.5 выполнены реальные импорт и экспорт OVA, OVF и ISO в двух тестовых тенантах Cloud Director API 39.0, с API refresh token и логином/паролем. Результаты, проверки повреждённых файлов и границы прогона перечислены в отчёте. Реальный S3 в этом прогоне не проверялся.
- Windows-приложение собрано и визуально проверено локально. Linux не входит в текущую поддержку и требует отдельной проверки, включая защиту ключа локального адаптера в аргументах процесса.
- Неподдерживаемая индивидуальная выгрузка ВМ из общего vApp блокируется, а не маскируется под экспорт одной ВМ.
- Размер API может быть оценочным. Если размер неизвестен, интерфейс просит верхнюю оценку вручную; требуется место под весь промежуточный образ. Сжатие, thin provisioning и кэш ОС влияют на скорость и фактический объём.
- «Диск» — скорость записи OVF Tool по счётчику I/O операционной системы, не независимый замер физической производительности накопителя.
- Проверка пакета и квоты не гарантирует аппаратную совместимость и успешное размещение в конкретном ЦОДе. ISO проверяется структурно (ISO9660/UDF) и читается полностью; работоспособность гостевой ОС, загрузчика и каждого файла внутри ISO не проверяется.
- Повтор после ошибки начинает передачу заново. Продолжение произвольной прерванной операции OVF Tool не заявляется.
- SSO через интерактивный браузер, нестандартные HTTP-прокси, отключение проверки TLS и автоматическая установка OVF Tool не входят в эту версию.

## Исходники

`src/ui.rs` — нативный интерфейс; `api.rs` — Cloud Director; `bridge.rs` — адаптер авторизации, потока и скорости; `ovf.rs` — запуск и проверка пакетов; `jobs.rs` — очередь, отмена, измерения и место; `s3.rs` — multipart upload; `store.rs` — настройки, журнал и экспорт секретов.

Тестовая программа `mock-ovftool` собирается только с feature `test-fixtures`, не включается в дистрибутив и не используется приложением вместо настоящего OVF Tool.

Справочные источники: [OVF Tool](https://developer.broadcom.com/tools/open-virtualization-format-ovf-tool/latest), [API Cloud Director](https://developer.broadcom.com/xapis/vmware-cloud-director-api/latest/), [API-токены Cloud Director](https://blogs.vmware.com/cloudprovider/2022/03/cloud-director-api-token.html), [схема VMRecord](https://developer.broadcom.com/xapis/vmware-cloud-director-api/latest/doc/types/QueryResultVMRecordType.html).
